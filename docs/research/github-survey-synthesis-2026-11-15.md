## 2. 핵심 발견

### F1. "후보별 사람 승인 + AI 주문 불허 + fail-closed"를 함께 갖춘 저장소는 없다

30개 중 세 요소를 모두 갖춘 곳은 확인되지 않았다. 부분 사례는 다음과 같다.

| 요소 | 사례 | 비고 |
|---|---|---|
| 건별 사람 승인 | nofx Frontier(승인 전 계정·수량·진입·청산 표시), OpenAlice(stage→commit→사람 승인 후 push, 기본 off 스위치) | 둘 다 "AI push 허용" 같은 우회 스위치/Autopilot이 있다 |
| 평가와 주문의 프로세스 분리 | QuantDinger("평가자 프로세스가 거래소 주문을 직접 제출하지 않는다"), OpenAlice(UTA 별도 프로세스) | QuantDinger는 에이전트 T-scope 주문 경로를 제공한다 |
| AI 조회 전용 | daily_stock_analysis(증권사 연동 조회 전용) | 우리 원칙에 가장 가까운 구조 |
| 불확실 제출의 fail-closed | nofx(조회 후 재제출 방지, 미해결 시 신규 진입 중지), QuantDinger(대사 미확인 델타 시 같은 방향 진입 중지) | |

**함의:** 이 결합은 외부 사례 없이 우리가 직접 설계·검증해야 한다. 현재 설계(후보별 승인→재검사→예약→outbox, 접수불명 재전송 차단)는 외부 어느 곳보다 구조적으로 앞서 있다(C1 인벤토리). 단 "있음"은 SQL·계약의 존재이며 운영 검증이 아니다.

### F4. 정정·기업행동(FU-15)

- 정정은 **보상 이벤트 추가**가 지배적이다. TigerBeetle은 정정용 `code`와 같은 `user_data_128`로 원본을 연결하고, Formance는 revert 거래를 추가한다. beancount·ledger·hledger는 파일 편집이며 불변성을 Git 같은 외부 수단에 맡긴다. Medici의 `void`는 원본에 플래그를 쓰므로 완전한 불변이 아니다.
- 소급 정정 시 저장된 잔액이 어긋날 위험(Medici 캐시 경고). 이벤트 재계산형(beancount 계열)이 안전하다.
- 분할: beancount는 "기존 포지션을 0으로 만든 뒤 조정 단가·수량으로 재추가, 총 원가 유지·실현손익 0". 배당은 Income 계정 거래.
- **빈 영역:** 대여·권리락·분배는 참고 구현을 찾지 못했다. 한국·미국 기준으로 직접 설계해야 한다.
- 라이선스: Formance(MIT), TigerBeetle(Apache-2.0), Medici(MIT), ledger(BSD-3)만 코드 차용 가능성이 있고 beancount(GPL-2.0)·hledger(GPL-3.0+)는 개념 참고만 한다. 실제 차용은 의존성 ADR이 선행한다(`dependencies = []`).
- 기존 결정은 미지원 정정·입출금 정정을 보수적으로 남겼다([EXECUTION-DEC-002](../decisions/EXECUTION-DEC-002-correction-performance-scope.md)). FR-06·AC-19의 지원 범위를 어디까지로 할지는 사용자 결정이 필요하다.

### F5. AI 팀 권한·공급망·감사

- **위협 17종**(MCP Security Best Practices, OWASP LLM Top 10 2025, OWASP Agentic Top 10 2026 기반): 도구 설명 변조, 승인 후 변경(rug pull), 간접 프롬프트 주입, 과도한 권한, confused deputy, 토큰 전달, 비밀 유출, 악성 패키지, 로컬 MCP 서버 침해, 클라이언트 RCE(mcp-remote CVE-2025-6514), MCP Inspector CVE-2025-49596, SSRF, 세션 하이재킹, skill 내 셸 실행, 하위 agent 권한 상속, 훅 우회, 무제한 소비. 일부(postmark-mcp, mcp-remote)는 2차 출처만 확인했다.
- **핵심:** 훅과 skill은 절차 보조일 뿐이며 강제는 **서버 측 scope 토큰, 샌드박스, managed 정책, 버전·digest 고정**에서 한다(AGENTS.md "실제 주문 통제는 실행 서비스에서 강제"와 일치).
- **Claude Code 운영상 주의점**(공식 문서 기준, 도입 전 재확인): 정책 훅은 exit 2여야 차단되고 exit 1은 통과한다. 훅 타임아웃은 기본이 통과라 `onFailure: block` 설정이 필요하다. 하위 agent는 `tools` 허용목록으로 제한하고 `Agent` 도구를 빼면 재귀 위임이 막힌다. 부모가 `bypassPermissions`이면 자식도 같은 모드를 따르고 자식 설정은 무시된다.
- **MCP 노출 사례:** OpenBB(카테고리 allowlist, route 단위 expose, 127.0.0.1 기본 — 그러나 기본 전체 노출·인증 미설정·서버 디스크에 쓰는 `install_skill`은 회피), wealthfolio(토큰 해시·scope·만료·폐기, `mcp_audit_log`에 성공/거부/오류 기록), QuantDinger(에이전트 토큰 scope R·W·B·N·T, 주문 scope 기본 비부여, 멱등키·확인 플래그·금액 상한·킬스위치). Alpaca 공식 MCP는 기본값이 "모든 도구 활성"이고 확인 플래그가 없어 반면교사다.
- **빈 영역:** 불변 감사 로그(append-only, 해시 체인)와 **작성자≠검토자**를 구조로 강제하는 오픈소스는 찾지 못했다. ai-hedge-fund의 해시 체인 원장은 금융 이벤트용 참고가 된다. AI 팀 감사는 직접 설계한다.
- AI 환경 파일 사례: ai-berkshire(`skills/` 정본, `codex-skills/`는 `sync` 스크립트가 생성하고 `--check`로 검증), QuantDinger(AGENTS.md 정본·도구별 진입점은 얇게), wealthfolio(AGENTS.md가 "Architecture impact" 노트 요구), Nautilus(기여자 AI 규칙: 실거래 위험 경고·정확한 산술·테스트 약화 금지·무허락 commit/push 금지).
- 회피: AutoGen(아카이브), 출처·라이선스가 불명확한 IBKR 커뮤니티 MCP, 프롬프트 필터만으로 주입을 막는 설계.

### F6. 운영 AI 작업의 복구·예산·승인 대기

- 8개 런타임(LangGraph, OpenAI Agents SDK, Temporal, Prefect, Hatchet, Inngest, Restate, DBOS) **모두 호출·비용의 예약→소비→정산 모델은 문서에서 확인하지 못했다**(OpenAI SDK는 사용량 기록만). 예산 영속은 직접 구현이 맞다는 근거다.
- **DBOS가 가장 비슷하다:** Postgres 단독, 서버 없음, workflow ID가 멱등키, 완료된 step 출력 재사용, `recovery_attempts`·`deduplication_id`·타임아웃·취소. Python SDK 종속과 결정성 제약이 따른다. 도입이 아니라 자체 구현 점검용 비교 대상으로 쓴다.
- 승인 대기의 **만료**는 Inngest·DBOS만 확인했다(LangGraph `interrupt()`는 문서상 무기한). 승인 만료·취소 상태는 직접 정의한다(우리 승인 상태에는 이미 expired 등이 있다).
- 장애 전이 표에 추가할 후보: 취소 중/취소됨 분리, lease 만료 크래시 감지, 최대 복구 시도 초과 종료 상태, 승인 거절과 취소 구분, resume 재실행 시 부수효과 중복 방지, 고아 예산 예약 회수, 호출 성공 후 결과 저장 전 크래시(정산 멱등), 작성 호출과 위험 검토 호출의 operation 분리, 큐 지연과 실행 타임아웃 분리, 재개 시 코드 버전 불일치.
- 라이선스·운영 부담: Inngest SSPL, Restate BUSL(미확인), Temporal·Hatchet은 별도 서버가 필요해 로컬 단일 사용자에게 과하다.

### F7. KIS Open API (공식 샘플 저장소 기준, 공식 포털은 못 열었음)

- 연속 조회: 응답 `tr_cont`가 M/F면 계속하고 `CTX_AREA_FK/NK`를 그대로 넘긴다. 공식 샘플은 max_depth(10)에서 경고 후 중단하므로 **불완전 결과를 "미체결 없음"으로 판정하면 안 된다**.
- 응답 판정은 HTTP가 아니라 `rt_cd`·`msg_cd`. HTTP 200이어도 실패일 수 있다.
- 체결 최종성·응답 유실 처리에 대한 공식 지침은 샘플에 없다. 체결통보(WebSocket, AES256 암호화, `CNTG_YN`=1 접수/2 체결)와 REST 조회를 이중 경로로 대사해야 한다.
- 모의 제약: 미국 모의 주문은 지정가만, 미체결 조회·일부 계좌 요약은 모의 지원 미확인, 모의 페이지 크기가 더 작음(15·20건), 미국 매도 모의 TR이 소스 안에서 코드와 주석이 충돌한다.
- 호출 제한 수치는 출처마다 다르다(공식값 미확인). 토큰 재발급은 분당 1회.
- 한국 시장 저장소 9개: 주문 기능이 있는 래퍼는 모두 체결 확인·미체결 상태 머신 근거를 확인하지 못했다(기존 결론과 같음). pykrx·FinanceDataReader는 스크래핑 기반이라 데이터 약관 위험, pykrx는 라이선스 미확인. 인터페이스 설계 참고는 python-kis(MIT)가 가장 가깝다.
- **미확인:** 시세 TR, hashkey, 오류 코드 전체표, 공식 호출 제한, KIS 저장소 라이선스.

### F8. 주문 안전장치와 PostgreSQL 내구성

- 사고 사례(Knight Capital 2012, Goldman 2013, Citi 2022 등, 출처는 보도자료·요약이며 SEC 명령 본문·FCA 최종 공시문은 직접 읽지 못함)에서 반복되는 통제 실패: 배포 불일치, 입출력 수량 대조 부재, 경고만 있고 거부 없는 한도, 노출 계산 주기가 길고 자동 차단 없음, 경보를 조치로 연결하지 않음.
- 규정(법률 자문 아님, 설계 참고): SEC Rule 15c3-5의 사전 점검(신용·자본 한도, 가격·수량 이상 및 중복 주문 거부, 통제의 배타적 보유로 우회 방지)은 개인 단일 사용자에게도 적용 가능한 항목이 많다. MiFID II RTS 6의 킬 기능·사전 통제는 조문 전문을 못 읽었다. 한국 알고리즘 거래 세부 기준은 미확인.
- PostgreSQL(현재 안정 18, 공식 문서 기준) 실패 유형 12개 중 핵심: 직렬화 실패(40001)는 전체 트랜잭션 재시도 후 소진 시 fail-closed, 세션 advisory lock은 롤백 후에도 남을 수 있으니 락 소유만으로 단일 실행자를 증명하지 않음, COMMIT 응답 유실은 요청 키로 재조회하고 불가하면 중단(공식 서술은 못 찾음), `synchronous_commit=off`·`fsync=off` 기동 시 검사, pg_dump는 PITR이 아니며 복원 검증 필요, 마이그레이션은 `lock_timeout`·주문 경로 정지, SECURITY DEFINER는 `search_path` 고정과 PUBLIC EXECUTE 회수.

### 4.2 계약·ADR·결정 후보

- **ADR 후보:** (a) lot 추적과 원가 방식(평균/FIFO) 도입 여부(FU-10·세금 계획과 연동), (b) 자체 AI 작업 영속 구현 vs 외부 런타임 도입(비교 근거: F6), (c) 코드·라이브러리 차용이 필요해질 경우의 의존성 판정표.
- **계약 갱신 후보:** BrokerPort 합성 어댑터 계약에 반영할 8개 — 환경별 TR_ID 매핑 분리와 `unsupported_in_paper`, 주문번호·원주문번호·`KRX_FWDG_ORD_ORGNO` 보관, 연속 조회 중단 시 `incomplete`, WebSocket+REST 이중 대사, `rt_cd` 기반 판정과 `unknown` 상태, 호출 제한의 설정화, 합성 픽스처의 장애 재현(페이지 분할·역순 통보·응답 유실·모의 미지원).
- **사용자 결정 후보:** 정정·기업행동의 지원 범위(FR-06), 분할 시 원래 취득일 보존 규칙, 원가 방식, 상태불명 주문의 최대 보류 기간과 수동 해소 절차.

### 4.3 요구서 자체의 점검 결과 (Codex C2, 94개 ID 대조)

추적성은 **부분 충족**이다. AC·FU 번호 연결은 있으나 요구별 계약·결정·실행 증거까지는 닫히지 않았다.

- **직접 AC 없음:** 비율형 비용, FU-08(시도 기록·정책 비교).
- **FU 특정 불가:** NFR-01~07·09가 "해당 FU"로 끝난다.
- **AC 부분 누락:** UT-02(중복 도입·수동 거래 불일치), FR-04(전달 불명·복원 실패), UI-03(필요 행동·재시도 시점).
- **새 계약 없음:** 정책·구성기·리밸런싱·시도원장·비율비용·FR-07은 기존 계약 기반이나 새 동작의 완성 계약이 없다.
- **문서 간 불일치:**
  - `product-read`는 "최종 확인 전", 전달 계획은 "최종 검토 완료". `product-artifacts`도 미구현 표기와 후속 수용 기록이 공존.
  - FR-06·AC-19가 포괄적인데 기존 결정은 미지원 정정·입출금 정정을 보수적으로 남김.
  - 요구서는 트리거 선택을 ND-03에 묶었으나 델타 분석은 ND-02(최종 선택)와 ND-03(값)을 구분. `FU-04←ND-03←비교←FU-08←FU-04` 잠재 순환의 해소 설명이 없음.
  - 거래세 0.20%의 지위가 작업 목록(원문 미확인)과 델타 분석(1차 확인으로 정정)에서 다름.
- **수정 제안 8개:** 각 ID에 계약 절·결정·증거·입력 버전 연결 / 비율비용·FU-08 독립 AC / NFR별 담당 FU·측정법·합격선 / UT-02·FR-04·UI-03 실패 조건 보강 / 정정·기업행동 지원·보류 범위를 AC-19에 명시 / ND-02·03·27 대응표로 순환 해소 / 계약 머리글을 설계 채택·부분 구현·수용 완료로 갱신 / 과거 PASS와 동일 버전의 새 요구 수용 증거를 별도 열로 관리.

## 5. 사용자 인터뷰 질문 (Codex C3, 우선순위는 분석 제안)

요구서는 사용자 인터뷰 없이 작성됐다([요구서 §8.4](../requirements-next-version.md)). 답변은 모두 미확인이다.

**P1 안전·정책·핵심 과업:** 1) 본인 단독 계좌 가정에서 빠진 사용자나 계좌 상황은? 2) 정책 입력 전 자산배분·현금·손실 제한의 결정 순서는? 3) 합계·단위 오류를 어디서 어떻게 설명해야 스스로 수정하는가? 4) '거래 없음'을 납득하려면 어떤 이유와 수치가 필요한가? 5) 위험 축소 후보 승인 시 먼저 볼 손실·위험 정보는? 6) 만료 직전 승인이 거부되면 어떤 설명과 다음 행동을 기대하는가? 7) '중단' 후 기존 주문은 어떻게 될 것으로 예상하는가? 8) '접수 상태불명'을 보면 무엇부터 하겠는가? 9) 키보드로 후보 확인→CLI 승인→결과 확인을 이을 때 어디서 길을 잃는가?

**P2 이해·복구:** 10) 보유 도입 자료와 원가 누락·중복·수동 거래 차이의 검수 방법 11) 분석 판단 시 먼저 보는 근거·반론·차단 정보 12) 비중의 분모·%와 %p·최소 거래금액·가용금 중 혼동되는 표현 13) 매도 후 매수 대기와 수동 환전 필요의 진행 표시 14) 배당·분할·정정으로 보고가 바뀔 때 비교하고 싶은 것 15) AI 예산의 예약·소비·정산 중 의사결정에 쓰는 값 16) UTC·시장 현지·한국시간 중 기본 표시와 원통화·KRW 병기 방식 17) 복원 후 재개 결정에 필요한 확인 결과 18) 예상 종목·기록 규모, 허용 조회 지연·복구시간·자료 손실.

**P3 도입·완료 판단:** 19) 설치·업데이트 실패 때 혼자 해결할 범위와 필요한 안내 20) 합성 여정 후에도 어떤 미완료 관문이 보여야 완료 범위를 오해하지 않는가.

화면 명세 대조(C3): 조회·상태 설명은 상당 부분 명세됐고, **정책 입력 양식·보유 도입 검수·위험 축소 화면·거래 없음/실현 불가 표현·정정 전후 비교·화면→CLI 전환**은 명세가 없거나 일부다.
