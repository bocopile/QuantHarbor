# EXEC-DEC-003 — 계획 작업 우선 진행과 실패 후속 큐

- 날짜: 2026-10-30
- 관련 작업 ID: Q27~36, P28-01~08, P29-01/02, RETURN-01/02
- 상태: 채택
- 결정 담당·요청 근거: root. 사용자 “전체 작업이 다 끝날 때까지 진행”, “테스트 실패로 필요한 추가 작업은 별도 큐”, “우선 계획된 작업 전체적으로 진행” 지시.

## 요구와 확인 사실

기존 전체36개·로컬10개·제품 하위12개는 유지한다. Q27은 최신 전체 검증 중이다. 개별 테스트 수정과 재검증을 반복하는 동안 독립적인 후속 설계까지 대기시키던 순서를 조정한다. 과거 실패·수정·미실행과 현재 완료 수는 보존한다.

## 선택과 이유

1. [실패 후속 큐](../tasks/failure-followup-queue.json)에 원래 작업 ID·발생 버전·종류·영향·담당·상태·차단하는 완료 관문·수정/재검증 증거를 기록한다. 과거 해결된 실패도 이력으로 남긴다.
2. 착수 가능한 원래 계획 작업을 먼저 진행한다. 선행 산출물의 계약과 소유권이 준비되면 설계 및 격리된 구현을 착수할 수 있다. 해당 선행 작업의 검증이 대기 중이면 통합·완료 조건으로 계속 연결한다.
3. 제품 하위 큐의 기존 `depends_on`과 Q27 관문은 **통합·완료 의존성**이다. 새 `start_dependencies`와 `stage`가 독립 착수 조건과 산출물 준비 상태를 나타낸다. artifact_ready는 completed가 아니다. 공통 계약이 불명확하거나 실제 결함이 해당 작업을 막으면 그 항목만 blocked로 두고 다른 준비된 계획 작업으로 이동한다.
4. 실패를 큐로 옮긴 것만으로 테스트를 통과시키거나 필수 수용 조건을 면제하지 않는다. 계획 산출물 작성 후에는 해당 후속 큐를 해소하고, 같은 최종 입력의 영향 검증·독립 검토·통합 기준을 충족해야 완료한다. 전체 종료 조건에는 미해결 필수 후속 작업도 포함한다.
5. root가 배정/결과/큐를 통합하며 전문 worker1·작성자1·재귀 위임0을 유지한다. 이미 시작한 고정본 검증은 별도 결과 영역에서 계속할 수 있다. 작성자는 그 검증 입력을 수정하지 않는다. 큐 파일은 절차 기록이며 자동 dispatcher나 백그라운드 agent를 새로 구현하지 않는다.

P28-01의 화면·사용 흐름 설계부터 착수한다. Q27이 미완료인 동안 그 상태를 화면/완료표에 명시한다. P28/P29의 후속 산출물도 위 착수/통합 기준을 적용한다. 실제 연결이 필요한 RETURN-02/Q30 이후의 행위는 기존 입력·정책·권한 관문을 따른다.

## 미확인과 재검토 조건

착수 조건 조정은 실제 계좌·키·주문·자금·새 지출·외부 전송·Git 원격 변경의 허가가 아니다. 필수 입력이 필요한 시점에는 준비한 구체안과 남은 입력을 정리한다. 실패 원인이나 계약 버전이 달라지면 영향받는 의존 항목과 재검증 범위를 갱신한다. 진척은 기존 완료 수와 별도의 artifact_ready/실패 큐 상태로 보고한다.
