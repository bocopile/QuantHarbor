# Git·worktree·커밋·머지 운영 전략

기준일: 2026-10-23. 관련 작업 ENV-01·02·09, C02·04·06. 사용자 요청에 따른 운영 전략이며 실제 Git 변경을 수행하거나 AP-06 실행 권한을 부여한 문서가 아니다.

## 현재 저장소와 첫 전환

읽기 조회 결과 현재 브랜치는 `main`, HEAD는 `ec56042`(Initial commit)다. 추적 파일은 README 한 개이고, 이후 작업의 문서·설정·스크립트·테스트는 미추적 상태다. 기본 checkout 한 개가 있으며 현재 대화에 연결된 관리 worktree는 없다. `origin` 이름의 원격은 존재하나 이번에 URL·가시성·권한·보호 규칙·최신 원격 HEAD는 조회하지 않았다.

첫 전환은 기존 파일을 보존한 현재 checkout에서 진행한다. 승인된 범위로 공개 파일 목록과 실제 diff를 검토하고, 로컬 전용 설정·개인/운영 데이터 제외를 확인한 뒤 `codex/env-baseline` 작업 브랜치에 기준 커밋을 준비한다. 파일을 비우거나 checkout을 초기화하지 않는다. 새 worktree는 기존 미커밋·미추적 작업을 자동으로 가져오지 않으므로 기준 커밋 전의 새 worktree를 현재 작업의 복제본으로 취급하지 않는다.

기준 커밋은 다음의 논리적 묶음을 권장하되 의존성 때문에 독립 검증이 어려우면 연결된 묶음을 함께 보존한다. 줄 수나 agent 수로 커밋을 나누지 않는다.

| 묶음 | 내용 | 조건 |
|---|---|---|
| 기록·요구·조사 | README, 공개 작업 지침, 요구·조사·결정·현재 상태 | 사용자 변경 보존, 과거 조사 시점·미완료 명시 |
| 개발 환경 | 공개 역할·Skills·Hook 정의, 정책·설정 예제 | 비밀값·실제 연결 식별값 제외. Hook 미신뢰를 완료로 표시하지 않음 |
| 검증 도구·증거 | 로컬 검사·감사 코드, 합성 테스트, 비민감 증거 | 코드/테스트/증거 의존성 일치, 실행 당시 버전과 현재 버전 구분 |

이 전환은 전체 제품이 완료됐다는 뜻이 아니다. 처음에는 검토된 개발 기반과 미완료 상태를 보존하는 기준점이다. 커밋 대상이 정해지기 전 `git add .`로 전부 담지 않고 파일을 명시해 선택한다. 실제 커밋은 대상 목록·변경 요약·민감정보 제외 확인·검증 결과를 준비한 뒤 AP-06 범위에서 수행한다.

## 브랜치

| 브랜치 | 용도 | 수명·규칙 |
|---|---|---|
| `main` | 검토·검증 결과를 통합한 기준 | 기준 커밋 전환 후 직접 기능 개발 금지. 실전 배포·거래 승인과 별개 |
| `codex/<작업-id>-<설명>` | 하나의 검토 가능한 논리적 변경 | 예: `codex/q04-hook-audit`. 머지 후 재사용하지 않음 |
| `codex/hotfix-<작업-id>-<설명>` | 운영 중 긴급 수정 | 지정 배포 SHA 또는 main 중 실제 대상에서 분기. 일반 검토·핵심 검증 유지 |

상시 `develop`·agent별 영구 브랜치는 만들지 않는다. 현재는 작성자 한 명의 순차 개발이므로 하나의 통합 기준과 짧은 작업 브랜치로 충분하다. 여러 버전의 병행 유지·독립 배포 일정이 실제로 생기면 release 브랜치를 별도 결정한다.

기본적으로 최신 확인된 main에서 분기한다. GitHub가 작업 기준이 된 뒤에는 원격 상태를 갱신·확인해 정확한 base SHA를 고정한다. 임의의 `pull`로 사용자 변경을 섞지 않는다. 선행 브랜치가 아직 머지되지 않았으면 기본적으로 그 머지를 기다리며, 긴 stacked PR 체인을 만들지 않는다.

## worktree

**작업 또는 고정 검토 버전별 worktree**를 필요할 때 사용한다. AI 역할마다 별도 checkout을 상시 만들지 않는다.

| 상황 | 사용 방식 |
|---|---|
| 순차 구현 | 기본 checkout과 분리할 필요가 있을 때 활성 작업용 worktree 한 개 |
| 읽기 검토 | 검토 대상 SHA·diff를 고정해 확인. 파일 변경이 없으면 추가 worktree 불필요 |
| 독립 재현·검증 | 필요할 때만 대상 SHA의 detached worktree를 만들고 검증 결과 반환 |
| 향후 명시 승인된 병렬 작업 | 독립 작업별 브랜치/worktree. 공통 계약·migration·lockfile 작성자는 여전히 한 명 |

현재 상한은 원본 checkout + 작업용 한 개 + 필요한 검토용 한 개를 기본으로 한다. worktree가 여러 개라도 전문 worker·작성자는 현재 정책대로 한 명씩 실행한다. 관리 worktree가 이미 있으면 재사용 가능성을 확인하고, 새로 만들 때 시작 ref를 명시한다. 승인·인증·운영 파일을 복사하거나 신뢰를 우회하지 않는다.

생성 후 확인: 실제 경로, base/head SHA, 브랜치, 상태, 작업 카드의 담당 파일, 필요한 명령·권한, 비밀정보 미복사. 같은 브랜치를 여러 worktree에 강제 checkout하지 않는다. 로컬 설정은 빈 예제로 준비하고 실제 자격증명은 필요한 프로세스에만 별도 주입한다. 자동 setup이 외부 설치·연결을 실행하는 경우 그 범위를 사전에 확인한다.

worktree는 Git 작업 파일을 분리하는 도구다. 비밀정보·프로세스·네트워크 격리는 기존 ENV-DEC-004와 운영 권한 정책을 따른다. Git worktree의 기본 동작은 [공식 문서](https://git-scm.com/docs/git-worktree)를 기준으로 한다.

## 작성·커밋

root가 base SHA·소유 파일·완료 기준을 배정한다. 구현 담당은 배정 파일만 수정하고 Git 이력 변경·push·merge는 root에게 인계한다. 공통 계약·상태·보드·큐·의존성·migration은 root가 통합하거나 한 명에게 명시 위임한다.

커밋은 설명하고 되돌릴 수 있는 하나의 변경 단위로 만든다. 해당 변경을 검증하는 코드·테스트·설명은 함께 관리한다. 의미 있는 중간 지점은 작업 브랜치에 보존할 수 있지만, 미완료 커밋을 main의 통과 결과로 취급하지 않는다.

형식: `type(작업-id): 변경 결과`. 예: `fix(q04): 감사 저장 실패를 성공으로 기록하지 않음`. type은 feat/fix/docs/test/refactor/chore/ci/revert를 사용한다. 본문에는 필요할 때 이유·영향·검증·미실행을 적는다. 변경량만 나열하거나 거짓 검증·작성자 정보를 넣지 않는다.

커밋 전 staged diff·파일 목록·제외 규칙·공개 가능한 설정/증거를 확인한다. 실제 로컬 설정·토큰·계좌·원시 로그·운영 데이터는 포함하지 않는다. 예제는 빈 값·더미·환경변수 이름만 사용한다. `.gitignore`는 이미 추적된 파일에 적용되지 않는다([Git 공식 설명](https://git-scm.com/docs/gitignore)). 비밀정보 탐지기의 실제 설치·실행과 과거 Git 이력 감사는 별도 수행 범위를 기록한다.

## 검토·PR·머지

기본 흐름은 `작업 브랜치 → 필요한 검증 → 독립 검토 → 수정 → 최종 버전 확인 → 승인된 push/PR → 검사 통과 → 승인된 squash merge`다. 아직 외부 Git 권한이 없으면 로컬 변경·검토 결과까지 준비하고 외부 동작을 보류한다.

PR은 한 가지 목적을 갖고 작업 ID, 해결한 문제·변경 동작, 검증과 미실행, 계약/DB 영향, 복구 방법을 포함한다. 실제 생성한 PR은 현재 대화에 연결한다. 리뷰 결과는 대상 HEAD 또는 입력 파일 해시와 연결하며 검토 후 의미 있는 변경이 있으면 해당 범위를 다시 검토한다.

일반 작업은 **PR 하나를 main의 논리적 커밋 하나로 합치는 squash merge**를 기본으로 한다. 중간 수정의 상세는 PR 기록·검토 증거로 추적한다. 별도로 보존해야 할 독립 커밋이 있으면 PR을 나누거나 이유를 기록해 merge commit을 선택한다. 기능과 trade-off는 [GitHub의 merge 방식 설명](https://docs.github.com/en/pull-requests/reference/pull-request-merges)에 근거한다.

통합은 root 한 명만 수행한다. 필수 검사·미해결 검토·최종 HEAD·base 변경·충돌 여부를 확인한다. main이 바뀌어 통합 결과에 영향을 주면 최신 base와 통합한 결과를 확인·검증한다. 성공한 옛 HEAD의 결과로 새 HEAD를 머지하지 않는다. 머지 결과 SHA와 PR·작업 ID를 연결하고 필요한 최소 기동 확인을 수행한다. 머지는 실전 배포·전략 승격·주문 실행을 자동 승인하지 않는다.

## 브랜치 보호·CI 목표

AP-06 승인 및 저장소 기능/권한 확인 후 main에 PR 경유, 필요한 상태 검사, 검토 대화 해결, force push·삭제 제한을 적용하는 것이 목표다. 검사명은 실제 존재하고 성공하는 job으로 연결한다. `.github/workflows` 파일이 있다는 사실만으로 CI가 동작하거나 보호된다고 기록하지 않는다.

독립 AI 검토 기록은 GitHub의 별도 계정 승인 review와 다르다. 실제 승인 가능한 reviewer 계정이 확보된 경우 required approval을 설정한다. 단일 계정에서 충족할 수 없는 보호 규칙을 설정하거나 AI 자신을 별도 승인자로 꾸미지 않는다. 부족한 GitHub 강제 조건과 로컬 절차 조건을 명시한다. 지원 범위·관리자 적용 여부는 [GitHub branch protection 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)와 실제 저장소에서 확인한다.

문서는 링크·설정 정합성, 일반 코드는 영향 범위 검사, 금융 계산·원장·승인·주문·권한은 관련 회귀·실패 시나리오와 필요한 보안 검토를 요구한다. 관련 코드가 없는 현재 상태에 형식적인 금융 테스트 통과를 만들지 않는다. 계약·workflow·배포·권한 변경에는 root 검토를 연결하고 향후 CODEOWNERS도 실제 계정 소유권에 맞춰 설정한다.

## 충돌·복구·정리

- 미공유 브랜치 정리는 권한과 변경 소유권을 확인한 뒤 가능하다. 공유 브랜치의 기록을 기본적으로 다시 쓰지 않는다. main 갱신은 승인된 범위에서 작업 브랜치에 통합하고, 충돌은 root가 양측 의도·계약을 대조해 해결한 뒤 필요한 재검증을 수행한다.
- 이미 머지된 결함은 원칙적으로 revert PR 또는 후속 수정 PR로 복구한다. revert는 기존 변경을 되돌리는 새 커밋을 만든다([Git 공식 문서](https://git-scm.com/docs/git-revert)). 데이터 migration·이미 발생한 주문/체결·외부 전송은 코드 revert만으로 되돌아가지 않으므로 별도 복구 절차를 따른다.
- `reset --hard`, `clean -fd`, force push, 브랜치 강제 삭제, 이력 재작성으로 문제를 덮지 않는다. 필요한 경우 영향·복구 경로와 명시 권한을 먼저 확인한다. 비밀값이 커밋에 들어간 사고는 보안 정책의 별도 대응을 따른다.
- 머지 후에는 정확한 PR·머지 SHA·최종 diff를 확인한다. squash merge는 원래 커밋의 조상 관계가 유지되지 않을 수 있으므로 `branch --merged` 하나로 정리 여부를 판단하지 않는다. 이후 작업은 갱신한 main에서 새 브랜치로 시작한다.
- worktree 정리 전 미커밋·미추적·ignored 파일의 필요한 산출물을 확인한다. 앱 관리 worktree는 해당 관리 도구의 archive 절차를 사용하고, 기본 checkout은 보존한다. archive의 복구 snapshot은 ignored 파일 보관이나 원격 백업을 대신하지 않는다. 비관리 worktree도 삭제 대상·복구 가능성을 확인하고 승인 범위에서 Git의 정리 명령을 사용한다.
- 릴리스는 검증된 커밋에 버전 tag와 변경·검증 기록을 연결하는 후속 단계다. 현재 제품/운영 준비 전에는 실전 릴리스 tag를 만들지 않는다. tag·공개 release·배포·자금 사용 권한은 각각 구분한다.

## 보드와 실행 권한

작업 보드에는 실제 확보한 branch, worktree 역할, base/head SHA, PR 링크, 검토·검증·머지 상태를 기록한다. 아직 없으면 미생성으로 표시한다. 개인 경로·계좌·원격 인증정보는 공개 보드에 넣지 않는다.

이번에 완료한 것은 전략 수립과 현재 상태 조회다. 실제 브랜치/worktree 생성·커밋·push·PR·merge·보호 규칙·CI는 적용하지 않았다. AP-06을 실행할 때는 로컬 기준 커밋과 외부 push/PR/merge/보호 설정의 허용 범위를 나눠 구체화한다. 일회성 또는 일정 범위의 지속 권한이 확보되면 같은 범위를 다시 묻지 않는다. 현재 미승인을 권한으로 바꾸지 않는다.

승인된 개발 작업에 필요한 비파괴적인 로컬 브랜치/worktree 생성은 해당 작업 범위에서 처리하며 별도 사용자 허가를 자동으로 추가하지 않는다. 보호된 Git 경로에 대한 도구 승인과 사용자 작업 권한은 구분한다. 이번 요청은 전략 수립이므로 이러한 생성 동작도 실제로 수행하지 않았다.
