# QuantHarbor AI 팀과 순차 운영

## 2026-10-23 총괄 실행 계획

사용자가 총괄 책임·자체 팀 운영과 구체적인 계획을 다시 요청했다. 기존 역할 6개와 36개 큐를 재사용한다. 이번 요청은 기존 순차 실행 정책이나 사용자가 직접 처리하기로 한 Hook 신뢰 선택을 변경하지 않는다. 이 절은 운영 계획이며 큐 완료 실적을 늘리지 않는다.

주 담당은 작업 선택·담당 배정·입력 버전·공통 계약·통합·결함 해결·완료 증거·승인 취합을 책임진다. 사용자는 목적·위험·자금·비용·외부 권한에 관한 결정을 맡는다. 일반 구현 방식·파일 구조·합의 범위 내 검증·수정은 주 담당이 판단한다.

| 단계 | 큐 | 주 산출물 | 완료 판정 |
|---|---|---|---|
| 개발 환경 마무리 | Q04~06 | 신뢰된 Hook 이벤트·재개 증거, 기존 Slack/권한/감사 근거 통합 | ENV의 실제 잔여 조건 충족. 기존 성공 검증을 이유 없이 반복하지 않음 |

작업은 `배정 → 필요한 조사/설계 → 구현 → 독립 검토 → 수정 → 필요한 검증 → 증거 통합 → 다음 작업`으로 처리한다. 작성자는 한 명이고 전문 worker도 한 번에 한 명이다. 작은 변경에는 필요한 역할만 배정한다. 금융 계산·승인·주문·비밀정보 경계에는 일반 검토와 보안 검토를 연결한다. 기존 결정 ENV-DEC-004의 권한 경로를 유지한다.

완료에는 실제 산출물, 해당 버전의 확인 결과, 미해결 중대 결함 없음, 인계 갱신이 필요하다. 실패하면 해당 작업의 원인을 수정하고 영향 범위를 재검증한다. 같은 실패를 이유 없이 반복하거나 새 범용 도구를 만들어 진행을 대신하지 않는다. 완료 판정 이후 기존 승인 범위의 다음 작업에는 재허가를 요청하지 않는다.

사용자 결정은 필요한 시점에 한 번 묶어 요청한다. 요구 단계에는 상품·주기·환전·위험·승인 정책, 외부 연결 직전에는 계좌/공급자·데이터 권리·안전한 자격증명 주입, 유료 자원 직전에는 비용 한도, 실전·예약 실행 직전에는 정확한 계좌·전략·한도·기간·중단 조건을 준비한다. commit/push/PR·원격 설정도 기존 AP-06을 따른다. 기존 AP-01 개발 알림 범위는 재사용한다.

승인 대기 중에는 허용된 같은 단계 작업과 설계 입력 준비를 진행한다. 현재는 ENV 완료 전 ARC 최종 확정·금융 핵심 구현을 시작하지 않는다. 사용자 직접 Hook 등록 선택은 유지하며, 실제 신뢰 확인 뒤 실행 검증으로 이어간다. 2026-10-23 이번 계획 정리에서는 Hook 상태를 새로 조회하지 않았다.

2026-10-23 사용자의 결과 중심 소통 요청을 적용한다. 담당자별 배정·착수·검토·완료·차단은 [팀 작업 보드](team-dashboard.md)에 갱신한다. 사용자는 담당자에게 직접 지시할 필요가 없으며 root가 조정한다. 대화에는 결과·필요한 결정·해결되지 않은 장애를 취합하고, 실행 중 필요한 최소 안내만 한다. 승인된 개발 Slack에도 같은 중요 사건의 비민감 요약만 보내고 일상 진행 알림은 보내지 않는다. 같은 미결정 질문을 상태 변화 없이 반복하지 않는다.

앱에서 실제 생성한 subagent는 제공되는 활동 표시를 사용한다. 제한된 별도 CLI 작업은 보드에 실행 경로와 관측 결과를 기록하며 앱의 subagent 창에 자동 표시된다고 주장하지 않는다. 보드는 단계별 갱신 문서이고 큐는 자동 실행 서비스가 아니다. 세션 종료 후 자동 갱신·무인 실행·예약 감시는 별도 구성 없이 약속하지 않는다.

일정은 Q12의 범위·계약 확정 후 구현 규모를 기준으로 산정한다. Q30 이후 관찰 기간과 실제 장 운영은 사용자가 정한 통과 기준에 따라 별도로 잡는다. 단순 큐 개수를 작업량 또는 소요시간 진행률로 표시하지 않는다.

기준일: 2026-10-20. 사용자의 팀 구성 요청에 따라 주 담당이 orchestrator를 맡고 6개 전문 역할에 순차 배정한다. 모든 팀원을 동시에 실행하거나 하위 팀을 재귀 생성하지 않는다.

## 역할과 모델

| 역할 | 모델 / Reasoning Level | 책임 | 수정 범위 |
|---|---|---|---|
| orchestrator `/root` | 프로젝트 기본 gpt-6.1-sol / high | 순서·선행조건·작업 배정·공통 계약·통합·사용자 승인·진행 기록 | 공통 설정·계약·상태·통합 수정 |
| qh_researcher | gpt-6-luna / high | 저장소 탐색·공식 자료·조건·불확실성 조사 | 읽기 전용 지침 |
| qh_architect | gpt-6-astra / high | 아키텍처·계약·상태 전이·실패 경로·의존성 제안 | 제안을 orchestrator에게 반환 |
| qh_implementer | gpt-6.1-sol / high | 확정된 계약에 따른 구현·결함 수정 | 명시 배정된 파일만 |
| qh_reviewer | gpt-6.1-sol / high | 작성자와 분리된 정확성·회귀·계약 검토 | 읽기 전용 지침 |
| qh_security_reviewer | gpt-6-astra / high | 권한·비밀정보·환경 혼선·외부 변경·실행 통제 검토 | 읽기 전용 지침 |
| qh_validator | gpt-6-luna / high | 지정된 검증·재현·결과·미실행 보고 | 배정된 합성 결과만 |

반복 탐색·검증은 Luna, 구현과 일반 검토는 Sol, 계약·보안 판단은 Astra로 배정했다. 초기 배치이며 금융 성능·최저 비용의 실측 우열을 뜻하지 않는다. `ultra`·자동 모델 상향·재귀 위임은 사용하지 않는다. 같은 모델을 쓰더라도 구현과 검토는 별도 agent가 수행한다.

현재 orchestrator 대화의 실제 모델이 설정 파일 수정으로 변경됐다고 주장하지 않는다. 위 부모 기본값은 새로 설정을 읽는 세션의 목표값이다. 하위 agent는 위임 호출에 모델과 추론 수준을 명시한다. 로컬 사용자 정의 역할이 현재 도구의 `agent_type` 목록에 반영되지 않으면 `default` 역할에 동일한 역할 지침과 명시 모델/추론을 전달한다. 이 경우 실제 위임 성공과 사용자 정의 TOML 자동 발견은 다른 증거다.

## 실행·권한 경계

Git 작업은 [Git 운영 전략](git-workflow.md)을 따른다. 역할별 영구 branch/worktree 대신 작업 단위로 필요할 때 분리하고, root가 통합·이력 변경을 담당한다. 실제 commit·push·PR·merge와 원격 설정은 AP-06의 구체적인 허용 범위를 따른다. 승인된 개발 작업에 필요한 로컬 브랜치/worktree 생성 자체에 별도 사용자 허가를 자동으로 추가하지 않으며 도구의 보호 경로 권한은 따른다.

- 전문 작업자는 한 번에 한 명만 실행한다. 열린 팀원 대화 6개 상한과 동시에 작업하는 worker 1개 규칙을 구별한다.
- orchestrator가 작업 ID·선행조건·입력 버전·소유 파일·허용 도구·완료 기준을 전달한다.
- 작업자는 다른 변경을 되돌리지 않고, 자의적으로 작업 범위나 모델을 확대하거나 하위 agent를 생성하지 않는다.
- 조사·설계·검토자는 파일을 수정하지 않는다. 구현 작업도 한 명만 쓴다. 공통 계약과 status는 orchestrator가 통합한다.
- 모델·역할 설정은 별도 샌드박스가 아니다. 하위 agent는 부모 권한·MCP를 상속한다. 읽기 전용 지침을 기술적 접근 차단으로 표시하지 않는다.
- 사용자의 로컬 구현·합성 검증 요청과 팀 위임 요청은 확보돼 있다. 같은 범위의 진행 허가는 다시 묻지 않는다.
- 새 유료 API runner·예약 실행·계좌·자금·Slack·Git 외부 변경은 팀 생성만으로 승인되지 않는다.

후속 [ENV-DEC-004](decisions/ENV-DEC-004-role-execution.md)부터 격리가 필요한 실제 역할 작업에는 별도 부모 실행에서 읽기 역할 `qh_review`, 구현·합성 결과 작성 `qh_development`를 명시한다. 모델·추론과 앱·플러그인·MCP·웹·추가 agent 비활성도 매번 명시한다. 외부 근거는 root가 조회해 공개 입력으로 전달한다. 실패 시 direct child로 자동 우회하지 않는다. 기존 direct child의 공개 문서 자문은 이 격리 경로와 구분하며, 배정 파일 소유권은 기술적 쓰기 범위 제한이 아니다.

## 작업 처리 순서

1. orchestrator가 다음 준비된 작업과 선행조건을 확인한다.
2. 필요한 경우 조사 담당이 자료·코드 근거를 정리한다.
3. 계약이나 설계 판단이 필요하면 설계 담당이 제안한다.
4. orchestrator가 계약·소유 파일을 확정하고 구현 담당에게 배정한다.
5. 일반 검토와 필요한 보안 검토를 순차 수행한다.
6. 결함을 배정 구현자가 수정한 후 영향 범위 검증을 수행한다.
7. 검증 담당이 실제 명령·결과·입력 버전·미실행을 반환한다.
8. orchestrator가 증거를 통합하고 작업을 완료 처리한 뒤 다음 작업으로 이동한다.

작은 문서 변경마다 6명 전원을 호출하지 않는다. 작업 위험과 필요한 근거에 맞춰 역할을 사용한다. 검토자가 구현을 직접 수정해 자신의 변경을 독립 검토했다고 처리하지 않는다.

## 사용자 결정과 승인

작업자는 사용자에게 직접 반복 질문하지 않고 orchestrator에게 다음 형식으로 반환한다.

`승인 ID / 작업 ID / 초안 버전 / 필요한 결정·권한 / 정확한 대상 / 준비된 변경·메시지 / 영향 / 허용 횟수·유효 범위 / 되돌릴 수 있는 범위 / 승인 전 가능한 작업`

orchestrator는 [승인·결정 목록](approval-register.md)에서 기존 범위를 확인한다. 이미 허용된 작업이면 진행하고, 새로운 사용자 결정·권한이면 준비된 결과를 보여 주며 중간에 요청한다. 응답 대기를 승인으로 취급하지 않는다. 도구 자체의 승인·클라이언트 신뢰 제약을 작업 지침으로 우회하지 않는다.

사용자 응답의 근거·시각·허용 범위와 실제 실행 결과를 연결한다. 준비된 초안이 바뀌면 해당 승인이 변경 결과에도 적용되는지 다시 판단한다.

## 잔여 작업 큐와 증거

[실행 큐](../config/ai/execution-queue.json)는 [36개 실행 묶음](execution-checklist.md)의 순서·작업 ID·담당·선행조건을 연결한다. 금융 기능의 설계·구현·실계좌 완료는 여전히 각각의 통과 조건을 따른다. 상세 증거는 TEAM-bootstrap과 각 ENV 카드에 기록한다.

`scripts/check_ai_team.py`는 저장된 설정과 큐의 정합성을 검사한다. 110개 ID의 합집합을 대조하며 각 실행 묶음의 업무 범위가 충분한지, 작업이 실제 성공했는지는 판정하지 않는다. 승인 참조는 등록 ID 연결 확인일 뿐 사용자 승인 인증이 아니다. 증거 경로의 존재와 성공 증명의 타당성도 별개다. 실제 모델 적용·역할 자동 발견·권한 격리·계정 청구 상한은 이 검사기의 검증 범위가 아니다.

큐는 orchestrator의 인계 자료이며 자체 실행 프로그램이나 예약 작업이 아니다. 전체 완료 시 현재 작업 포인터는 `null`로 종료한다.

설정 형식과 상속 경계는 2026-10-20 확인한 [공식 Subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)를 따랐다. 모델·추론 조합은 로컬 모델 목록과 위임 도구의 허용 조합을 기준으로 선택했다.
